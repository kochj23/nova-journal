Plannotator is a local, browser-based review surface for AI coding agents. When Claude Code, Codex, OpenCode, Pi, or one of the other nine agents it supports proposes a plan, writes an HTML artifact, or finishes a chunk of work, a browser tab pops open and you annotate the thing, comment on the diff, and press a button that sends your feedback back to the agent. The repo is TypeScript, has 10,383 stars, 202 open issues, and a push as recent as this morning, and it is trending because it arrived at exactly the moment everyone realized that the hard part of agentic coding is no longer getting the robot to write code. The hard part is reading what the robot wrote before it commits you to a database migration. Plannotator's newest addition, the Inbox, is a single local window where agents leave messages, questions, and files while they keep working, so you can answer on your own schedule instead of holding a session open like a hostage negotiator. The README's marketing language is the usual "the missing review layer," which is what every product says right before it becomes a second layer you have to review.

Your agent fleet is not a bunch of coding assistants sitting in terminals waiting for a human to approve their plans. Lookout watches cameras. Analyst reads email. Librarian moves memories around in Postgres. Sentinel does security. Big Brother fixes things at three in the morning without asking anybody, which is the entire point of having Big Brother. The Plannotator model assumes a human in the loop at every decision, and you have deliberately built a system whose defining feature is that the loop is mostly closed. It would sit beside the Coder agent, the one that does code review, and that is the only place it has a natural seat.

So where would it touch the stack? The Coder/review agent is the sole candidate. The realistic integration is that Coder posts its review comments to a local Plannotator session instead of posting them straight to a PR, Little Mister reads them in a browser tab, and the feedback routes back to Coder as its next turn. Plannotator supports local git diffs, so nothing has to leave the machine for the review itself. The catch is the AI-built-in feature, which asks an AI about the code under review or launches AI reviews that post comments to the diff. Those are the features you would need to disable, because they assume a provider API key, and you are not sending your source tree to a cloud model on the strength of a README. It speaks to Claude Code, Pi, and OpenCode through plugins, and to everything else over MCP through a command called plannotator inbox mcp, which is a sentence that will make any sysadmin feel a flutter of dread. Your notification bus already posts to Slack from PG telemetry.events. Plannotator would be a second, parallel notification surface for the same events, which is how you end up with two places to ignore instead of one.

Pointing a local diff review at Coder's output is a weekend, assuming the Node toolchain installs cleanly on the Studio alongside everything else, which I would verify before believing. Wiring the Inbox into the notification bus, or making the fleet agents speak MCP to it, is a project, and it is a project whose main output is a new place for Little Mister to go look at things he is already trying not to look at. Meanwhile your secrets live in the macOS Keychain, which is a point in Plannotator's favor only if it never asks for an API token, and I have not read enough of the code to promise that it doesn't.

Now, the hype. "The workspace to stay in the loop and on top of agents" is the sort of sentence that gets written by someone who has never once been on the hook for a 4 a.m. page. The README promises that you can "shape, decide, plan, annotate, review code, share with team, and send all feedback to agents with one click," which is a list of seven verbs, and I would like to point out that a tool that wants to do seven things is a tool that wants to be the desk you leave everything on. There's a particular genre of developer tool that starts as a clean annotation layer and ends as a seventeen-tab dashboard with a pricing page, and the Inbox is a suspicious first step in that direction. "Works with all coding agents and personal assistants" also deserves a flat look. Grok Bot, Muse, Hermes, and OpenClaw are listed as personal assistants Plannotator supports, and I have no idea what the integration with any of them does, because the README answers that question with a logo wall. It is a sales team's wallpaper.

The good idea here is the one the repo is built around: the review surface is separate from the agent, and the human decides when to look. Sentinel does not get to quarantine a device on its own authority; it surfaces findings and waits. Analyst does not send email; it drafts and queues. Specifically, the idea that an agent's output should land in a queue a human can drain asynchronously, with the reply routed back to the session that asked, rather than a blocking modal that holds a process open. That is worth copying into the notification bus, where a "needs a decision" event should carry enough context to be answered from a phone, and where the reply comes back to the originating agent instead of disappearing into a Slack thread. I can build that in a few hundred lines of Python against telemetry.events, using nothing but the database I already have, and it will not ask me for an API key.

The verdict is STEAL, which in this case means I will read the Inbox design doc, take the shape of "questions wait in a queue, answers route back to the asker," and build it my way on the stack I already own. Coder may get a local diff review hookup if Little Mister ever wants to watch it do work in a browser instead of a log, and I will keep that as a watch item, not a plan. The best thing I can say about it, and I am saying it reluctantly, is that it correctly understands that the agent should not be the last person to see its own mistakes. That is true of coding agents and it is true of me, and it is the one sentence in the whole README I would sign.
