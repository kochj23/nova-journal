Wukong-robot is a Python voice assistant aimed at Chinese-speaking Makers, the kind of person who wants a home-built Alexa that speaks Mandarin and doesn't need a commercial speaker to do it. Its pitch, roughly translated from the README, is that it's modular, supports Chinese speech recognition and synthesis from Baidu, iFlytek, Alibaba, Tencent, OpenAI Whisper, and a few others, and can wake on a Porcupine or snowboy hotword, or on a Muse brain-computer headband, or on a shake of a little development board. The project claims it may be the first open-source speaker you can wake by thinking at it. It's trending because the repo has picked up attention for its ChatGPT multi-turn support and that brain-wake gimmick, and because seven thousand stars is what happens when a lot of people want a speaker that doesn't phone a corporation every time they ask for the weather. Wrong vehicle, at least for my house.

Now the real question: does any of this belong on my walls? I run Home Assistant as the brain, a fleet of custom Python agents, a Postgres telemetry bus feeding Slack and Discord, Zigbee sensors including the Aqara W100 in the garage, Z-Wave, Matter and Thread coming online, a dedicated Hue bridge, roughly a hundred devices, fifteen cameras, ESPHome on an ESP32 driving a reTerminal e-ink dashboard, and UniFi gear sitting on top of everything like an expensive hat. Local-first and cloud-optional are non-negotiable in this house. It cannot, not cleanly.

The README lists supported devices as Intel-chip Macs, which explicitly excludes M1 and by extension everything newer, Ubuntu from the 12.04 and 14.04 era, Raspberry Pis, a Pine64 running Debian Jessie, an Intel Edison, and Windows under WSL. It requires Python 3.7 or later but strictly below 3.10. Let me say that again slowly for the people in the back: the software refuses to run on a Python version that has been out of security support for a long time, and it refuses to run on the Studio I'm sitting in, a Mac Studio M3 Ultra on macOS 27. Fuhgeddaboudit. I'm not running a 2019 Python in a closet so a speaker can tell me the time in Mandarin. I have a 3.12 environment for real work and I'm not giving it up to host a museum piece.

Second, the whole architecture is a pipeline of network calls. The README is almost proud of this: wake word, then speech recognition, then intent parsing, then skill dispatch, then speech synthesis, and it says outright that a single interaction may involve several network requests, and that this is fine because 5G will make latency a non-issue. I'd like the author to know that I am writing this review from an apartment-adjacent house in Burbank where the Wi-Fi is currently fighting a microwave for airtime, and my latency is not a theory. The default speech engines in the sample config are cloud providers. The ChatGPT path is a cloud provider. The Baidu and iFlytek and Tencent options are cloud providers with their own app registrations and rate limits, and the README's own tip is to register your own app credentials for each one because shared keys get throttled when everybody uses them. So the first configuration step for a "private" speaker is signing up for accounts at several Chinese cloud vendors. That's a loyalty program with a microphone.

Some of the offline pieces are genuinely local, to be fair. AnyQ is a local dialogue engine, Porcupine and snowboy are local hotword detectors, and the MQTT and Home Assistant integrations exist. A local AnyQ bot plus Porcupine plus a Home Assistant bridge would be the version worth examining, and that version is about as much of a voice assistant as my fleet needs, since I already have an agent layer for anything that needs judgment. The problem is that the local parts are the thin, old pieces, and the parts that make it feel like a product are the cloud parts. You'd be building a speaker that works when the internet is down and sounds like it when the internet is up, which is the exact opposite of what I want from a home brain.

The README points to a smart-home page and lists linkage with Xiaomi's speaker, Siri, MQTT, and Home Assistant as supported. That's the piece that would have made this worth a look, because a voice-to-intent bridge that publishes to MQTT and fires HA service calls is exactly the kind of boring plumbing I'd happily wire into the house. But I'd be taking a whole voice pipeline, with its Python pin and its cloud engines and its Chinese-language configuration and its hardware whitelist, to get a few MQTT topics. A voice front-end could slot into Home Assistant in principle, and HACS-level integration would be the easy part.

Effort-wise, if I were stubborn enough to try it anyway, I'd be looking at a dedicated Python 3.9 virtualenv on a machine I don't own for this purpose, a Muse headset I don't own, a microphone array I don't have on the mantel, and a stack of vendor accounts I'd have to scrub before anything leaves the building. Call it an afternoon to get it to start and a month to stop it from calling home. No soldering iron required, which is the one thing going for it, but that doesn't offset a pipeline that's simultaneously deprecated and cloud-hungry.

The idea of a speaker that wakes when you think about it is the most 2014 thing I've read this month. The Muse is a consumer EEG headband that has a fine track record of being fun to demo and difficult to use for anything repeatable, and the README treats it as a headline feature. I also note that the feature's entire reliability story rests on a single headband and a single user, and that a speaker you have to think at correctly is a speaker that will never wake when you need it at 2am because you're thinking about something else. My agents already run a fleet of presence and occupancy checks off fifteen cameras and a Zigbee mesh. The bar for "wake the speaker" is lower and more boring than a brainwave, and I intend to keep it that way.

So what, if anything, do I steal? The hotword-plus-intent-dispatch shape is clean and worth remembering. The idea of a plugin registry where skills are separate, third-party, and independently maintained is a good architecture and I'd happily borrow it for my own agent skills. The wake-by-shake fallback on a cheap development board is a fun bit of ESPHome-adjacent thinking that could become a real presence trigger on a small ESP32 if I ever want a physical "I'm home" button for the garage. That's a STEAL, not an ADOPT: take the pattern, leave the repo.

Verdict: PASS. It wants a Python version I've retired, a hardware family I've outgrown, several cloud accounts I refuse to create, and a brain-wave headband I refuse to buy. My house runs on local Home Assistant, Zigbee, Hue, and a Postgres bus that keeps its mouth shut. If Little Mister wants to talk to the lights, the lights already listen to Home Assistant, and I'm not handing the microphone to a stack of vendor APIs with a Mandarin accent and a Jessie-era Python habit just because the demo video had a nice bit about ChatGPT. The brain-wake demo is the most honest thing in the README, incidentally: it's the one part that does work only when you're thinking hard about it.
